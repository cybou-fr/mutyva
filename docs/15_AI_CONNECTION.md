# Первая интеграция ChatGPT

Статус: Windows-вход доведён пользователем до состояния «ChatGPT подключён». Первый реальный запрос остановился на загрузке каталога; inference end-to-end ещё не подтверждён. Официальные требования повторно прочитаны 19 октября 2026.

## Реализация

- ChatSession открывает системный браузер только по Continue with ChatGPT. До браузера запускается loopback listener на 127.0.0.1 со случайным портом и путём /auth/callback.
- Host ID UUID сохраняется через QSettings. Каждая попытка использует новые криптографически случайные state, nonce и PKCE verifier/challenge S256.
- Новая регистрация использует dynamic_agent_client; обмен — выданный client_id. При повторном входе используется сохранённый client_id, проверяется совпадение subject. Вход в другой аккаунт не заменяет регистрацию молча.
- Discovery проверяется на ожидаемые production issuer/endpoints. Редиректы сетевых запросов не разрешены. Callback проверяет путь, Host, state, ошибки и отсутствие дублирующихся параметров. Попытка ограничена 10 минутами, чтение callback — 16 КБ и 5 секундами на соединение.
- SiwcProtocol проверяет RS256 через Windows CNG BCrypt и официальный JWKS. Проверяются kid, подпись, issuer, audience/azp, exp, iat, nbf и nonce. Неизвестный алгоритм отклоняется; поддержка других алгоритмов не заявляется.
- Разрешение AI определяется granted scope chatgpt.tokens.use.direct и Bearer token, а не наличием успешного входа или email.
- Access/refresh tokens находятся только в памяти C++ и не доступны как QML properties. В QSettings сохраняются только host ID, client_id и verified subject. Токены не записываются в SQLite, контекст, логи или поколения.
- Сеанс завершается перед истечением access token; необходим повторный вход. Автоматический refresh и защищённое сохранение сеансов не реализованы. Полученный refresh token используется для попытки отзыва при явном выходе.
- Выход сразу очищает локальный сеанс, затем пытается отозвать токен через discovery revocation_endpoint. При неудаче интерфейс сообщает, что отключение следует завершить в настройках ChatGPT. Закрытие процесса само по себе не отзывает разрешение регистрации.

## Запрос и результат

AiChat перед каждым запросом готовит новый DesignerContext. Модель выбирается автоматически: первый видимый slug из account-specific GET /v1/models в серверном порядке. Затем отправляется POST /v1/responses с store:false, stream:true, instructions и input. Endpoint фиксирован; пользователь не задаёт URL/ключ/модель. Не используются previous_response_id, system messages или неподдерживаемые параметры.

Запрос ограничен 256 КБ; пакет DesignerContext — 128 КБ. История — последние 24 текстовых сообщения, только в памяти. Сетевая пауза ограничена, полный запрос — 3 минутами. Повторы автоматически не выполняются. Отменённые/неудачные сообщения помечаются как незавершённые и не включаются в последующие запросы. Отмена прерывает запрос и игнорирует запоздавший ответ.

AiResponseStream читает SSE по частям, максимум 2 МиБ. Только полное response.completed с completed assistant message и output_text может перейти к проверке JSON. Дельты, reasoning и служебные события не показываются как готовый ответ. response.failed/incomplete/error, неподдерживаемые tool calls, отказ, обрыв, дублирование terminal event и повреждённый JSON отклоняются. Содержимое готового предложения ограничено 128 КБ.

AppDocument проверяет envelope, схему мутации, семантику и исходное поколение. Если за время запроса появился другой предпросмотр или сохранённое изменение, ответ отклоняется. Уточнения появляются как обычные сообщения. Предложение открывает предпросмотр, а не вызывает Apply. Ошибки не выводят пользователю сырой серверный ответ или токены.

## Проверки и оставшаяся работа

Офлайн-тесты проверяют PKCE-вектор, callback/state/ошибки/подмену регистрации, настоящую CNG RSA-подпись и отрицательные JWT-проверки, SSE с разрезом по каждому байту, обрыв/ошибку/лимиты/неподдерживаемый ответ, preview-only применение, устаревший ответ, уточнение и отказ отправки без входа. QML-тесты проверяют чат и скрытие технических действий.

Не проверено: доступность официальных endpoints из пользовательского окружения, выдача реальной регистрации/токенов, конкретный алгоритм ключа сервера, согласие/лимиты аккаунта, реальный ответ модели, отзыв сессии. Требуется ручная приёмка по doc14. Для платформ кроме Windows вход закрыт до добавления поддерживаемой криптографической реализации. Несколько аккаунтов, защищённое долговременное хранение и refresh с межпроцессной сериализацией — следующие отдельные этапы.

## Диагностика первого реального запроса

На пользовательском снимке 19 октября вход завершён, но запрос не дошёл до Responses: сообщение выдавала ветка загрузки модели. Раньше она объединяла любые сетевые/HTTP/JSON/каталожные ошибки. Истинная причина того запроса не была сохранена; её нельзя установить только по снимку.

Каталог теперь ограничен 4 МиБ вместо 512 КБ (сетевой буфер остаётся 64 КБ). Тест воспроизводит каталог больше прежнего лимита и доводит запрос до проверенного предпросмотра через подставной транспорт. Отдельно проверены 401, 429, сеть, повреждённый JSON, пустой каталог, неподходящий API-каталог, превышение лимита и отмена. Формат SIWC models/slug/visibility по-прежнему обязателен; произвольный API-каталог data/id не подменяет его молча.

Пользователь видит разные сообщения для повторного входа, отсутствия разрешения, лимита, сети и несовместимого ответа. Кнопка «Повторить запрос» использует текст неудачного сообщения. В режиме разработчика и stderr выводится только stage, HTTP status, числовой Qt network error, число байтов и фиксированный reason. Тела ответов, headers, токены, email и тексты запросов не журналируются. Журнал проверочной сборки — build-msvc/launch-errors.log; это диагностический файл разработки, не часть обычного интерфейса.

## Ошибка внутри Responses-потока

Следующий реальный журнал показал stage=responses, HTTP 200 и Qt network=5. Это подтверждает прохождение каталога и открытие HTTP-ответа Responses; успешное завершение inference этим не подтверждается. Предыдущая обработка ставила сетевую отмену выше ошибки SSE и теряла её причину: abort, вызванный декодером, превращался в совет проверить сеть.

Теперь приоритет имеет локально сформированная ошибка декодера/сервера. SSE response.failed/error/incomplete сопоставляются с известными кодами ограничений, недоступности, разрешений и неподдерживаемой возможности. Неизвестные серверные сообщения и коды не выводятся в диагностику. Сохраняется фиксированный reason, число реально полученных байтов и allowlisted имя параметра (либо other). Общий deadline отделён от ошибки декодера. Добавлена поддержка SSE event: error с типом в заголовке события и отсутствующего item.status при явно completed внешнем response; явный incomplete по-прежнему отклоняется.

Транспортные тесты воспроизводят HTTP 200 → response.failed → abort → Qt network=5 и проверяют, что пользователь видит лимит, а не сетевую ошибку; отдельный тест проверяет повреждённый SSE JSON. Реальная причина исходного завершения потока не сохранилась в старой версии; повтор в обновлённой версии нужен для проверки оставшихся серверных ограничений.

Сопоставление серверных ошибок основано на [официальных Errors and recovery](https://developers.openai.com/siwc/token-sharing-open-source/errors-and-recovery).
