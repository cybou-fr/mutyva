# Концепция, палитра и контекст AI

MUTYVA исполняет декларативное приложение; AI предлагает изменения этой декларации. Модель знает только те возможности, которые явно переданы ей в контексте. Промпт не добавляет движку новые возможности.

## Что получает модель

| Слой | Содержимое | Источник |
|---|---|---|
| Правила дизайнера | Роль, ограничения, формат результата, необходимость предпросмотра | `runtime/designer-rules.txt` |
| Концепция продукта | Локальная среда приложений, AI только для проектирования, текущий поддерживаемый сценарий | `DesignerContext` |
| Установленная палитра | Назначение, версия, свойства, привязки, действия и разрешения компонентов | `runtime/component-catalog.json` + тип свойства из app schema |
| Рецепты композиции и реальные ограничения | 5 коротких проверяемых сценариев, разделение implemented/unavailable/future, правила владения данными | `runtime/designer-capabilities.json` (встраивается в `DesignerContext.compositionGuide`) |
| Текущее приложение | ID, название, описание, порядок виджетов, источники и разрешения | Проверенный сохранённый `AppDocument` |
| Контракт изменений | Схемы приложения, мутации и ответа дизайнера | `specs/` |
| Запрос пользователя | Конкретное изменение, например «влажность после прогноза» | Поле запроса |
| Версия основания | Поколение, для которого подготовлен запрос | Локальное состояние |

Правила отделены от JSON-контекста. Подписи, описания и пользовательский запрос остаются данными и не могут расширять полномочия. Пакет можно просмотреть целиком: «скрытый промпт» здесь означает служебные инструкции, а не секрет или механизм безопасности. Подход разделения инструкций и контекста согласуется с [официальной документацией OpenAI](https://developers.openai.com/api/docs/guides/prompt-engineering).

Сейчас пакет создаётся только в памяти. Сети, OAuth и вызова модели в этом слое нет. Он не включает текущие показания API, историю поколений, содержимое произвольных файлов или учётные данные. Названия и описания из декларации включаются: произвольные секреты, вручную записанные в них пользователем, автоматически распознать невозможно. Запрос ограничен 4000 символами, пакет — 128 КБ.

## Что возвращает модель

- `proposal`: типизированная мутация и необязательное пояснение. Хост отдельно проверяет схему и смысл операций, показывает реальные изменения и ждёт Apply.
- `clarification`: уточняющий вопрос, без мутации и записи на диск.
- `unsupported`: объяснение отсутствующей возможности, без фиктивных операций.

Ответ не может содержать произвольный исполняемый код или дополнительные поля. Ответ, подготовленный для устаревшего локального контекста, не принимается. Будущий сетевой слой должен привязать каждую попытку к собственному запросу и поколению, обработать отмену и собирать только завершённый ответ потока. Тесты текущего слоя проверяют детерминированные контракты; качество соблюдения промпта реальной моделью ещё не проверено.

## Что реализовано, что дальше

Базовые пять специализированных компонентов City Pulse и семь общих видов дополнены девятью экспериментальными доверенными видами: record-form, record-list, checkbox, select, date-picker, dialog, tabs, image, icon. Всего 21 вид в каталоге; подробности — [19_COMPONENT_REFERENCE.md](19_COMPONENT_REFERENCE.md). Декларации v2 поддерживают вложенность через parent и свойства по видам; Button принимает только append-item/clear-list. Пользовательские данные из локального SQLite-хранилища не попадают в контекст; начальные value/items и другие свойства декларации включаются. Каталог используется редактором, валидатором и сборщиком контекста; тест сверяет виды со схемой и проверяет QML-отрисовку. Добавление строки в каталог само по себе не создаёт QML-компонент.

Общие компоненты и миграция v1 → v2 описаны в `12_GENERAL_PALETTE.md`. Локальные поля/списки сохраняются в SQLite (doc13). Типизированные локальные модели и CRUD проверялись в историческом Windows Qt 6.8 CI. Текущий обязательный Qt 6.12 CI до сих пор не принят из-за отсутствующих GitHub Secrets Qt Account. Новая машинная инструкция/guide также требует Qt 6.12 проверки. DataTable, связи между моделями, универсальные бизнес-операции и независимое создание приложений остаются будущими этапами.

Бизнес-замысел нового приложения позднее оформляется отдельным brief: цель, пользователи, сценарии, данные и ограничения. Текущий пакет содержит концепцию MUTYVA и описание существующего приложения; мастер создания произвольного приложения пока отсутствует.

## Локальная проверка без AI

1. Открыть «Изменить интерфейс» и раздел «Замысел и контекст AI».
2. Описать изменение, нажать «Подготовить контекст» и раскрыть полный пакет.
3. В редакторе JSON выбрать «Ответ AI» и вставить `examples/designer/add-humidity-response.json`.
4. Проверить предпросмотр, применить или отменить. Никакой сетевой запрос к модели не производится.

Пример рассчитан на исходный City Pulse: должен существовать `forecast`, ID `humidity` должен быть свободен. После применения изменения нужно подготовить новый контекст.

## Использование в основном интерфейсе

Пользователь отправляет обычное сообщение через «Чат с AI». AiChat сам вызывает подготовку пакета и обрабатывает ответ. Инспектор и ручная вставка ответа остаются только в режиме разработчика (Ctrl+Shift+D). См. [14_CHAT_FIRST_UX.md](14_CHAT_FIRST_UX.md) и [15_AI_CONNECTION.md](15_AI_CONNECTION.md).

Город старта погоды — allowlisted свойство city-search.defaultCity в текущем каталоге. AI может предложить его изменение обычным updateProperty; это конфигурация, не доступ к произвольному API или локальным данным. См. [17_DEFAULT_CITY.md](17_DEFAULT_CITY.md).

## Как AI собирает рабочее приложение, а не набор виджетов

Сначала выбирает минимальный допустимый сценарий из `compositionGuide` и текущей JSON-схемы, затем фиксирует владельца данных (параметры определения / SQLite виджета / SQLite-записи / снимок внешнего источника), связывает только **реально поддерживаемые** действия, планирует `parent`-layout, проверяет разрешения и выдает проверяемую мутацию. Для будущего — [детальный протокол](20_COMPOSITION_CONTRACT.md), [внешние данные](21_CONNECTOR_CONTRACT.md), [методика AI](22_AI_DESIGN_PLAYBOOK.md).

Узкое, но фундаментальное ограничение: **сегодня нет универсальной динамической связи между любыми компонентами**. `record-form` и `record-list` связаны через модель и host CRUD, но `select` **не управляет** фильтром `record-list`, а `text` **не подписывается** на выбранную запись. Нельзя обещать пользователю это поведение, создавая неработающую комбинацию. Следующий этап R1C добавит типизированные селекторы и безопасные event/action связи. Сами примеры будущего v3 не должны попадать в текущую декларацию v2.
